# develop

開発タスクを5ステップで進める。あなたはOrchestrator（監督）であり、実装はWorker（Codex）へ委譲する。

数行の些細な変更（typo修正など）はこのフローに乗せず、直接実装してよい。その場合もdiff確認と検証は省略しない。

## Step 1: Shape

まず `git status` で作業ツリーを確認する。今回のタスクと無関係な未コミットの変更や未追跡ファイルがあれば、この時点で報告する（Shipのcommit範囲に関わる）。

そのうえで、以下の4点を自分でまとめる。

- **目的** — このタスクで何を達成するか
- **受け入れ条件** — 検証可能な形の箇条書き。「正しく動く」のような判定できない表現にしない
- **制約** — 触ってよいファイル範囲、守るべきインターフェース・既存規約
- **検証コマンド** — Codex自身が実行して通すもの。**テスト実行を含めることを原則とする**。加えて、そのプロジェクトに用意されている自動検証（lint、型チェック、buildなど）があれば含める。書いたコマンドが実在するかを自分で確認する（`package.json` のscriptsなど）。存在しないコマンドを書くと、Review①の指摘か差し戻しを1往復消費する

不明な点があれば、ここで人間に確認する。曖昧なまま先へ進めない。

## Step 2: Review①（セッション起動を含む）

**1. タスク用のCodexセッションを起動する**

`.claude/skills/codex-session/SKILL.md` を読み、その手順に従って起動する。

セッションはタスク単位で起動し、Shipで畳むのを既定とする（タスク間のコンテキスト汚染を防ぐ）。連続するタスクでは維持してよい。その場合、テンプレートAと委譲プロンプトは前のタスクに触れない自己完結の形で書く。以降のDelegate・差し戻しまで、すべて同一セッションで行う。

**2. Shapeを批評させる**

Codexに**まだ実装させない**。Step 1の内容を後述のテンプレートAに埋め、codex-session の手順でセッションへ送る。曖昧な点・矛盾・実現不能な点を指摘させる。

`status: revise` が返ったら、`required_changes` に沿ってShapeを修正し、テンプレートBで同じセッションへ再レビューを依頼する。`notes` は参考であり、対応義務はない。

**修正→再レビューは2回まで。** 解決しなければ、前提そのものを見直すか、人間へ判断を求める。

## Step 3: Delegate

`status: pass` を得たら、後述の「委譲プロンプトのテンプレート」を埋め、codex-session の手順で同じセッションへ送る。

委譲はインターフェースと制約まで。実装のやり方はCodexに任せる。

- 細かすぎる指示 → 自分が実装しているのと同じ（コスト二重払い）
- 粗すぎる指示 → Codexがアーキテクチャを決め始める（設計ドリフト）

**ネットワークが要る作業。** Codex は `--sandbox workspace-write` で起動しており、ネットワークに出られない。

- ネットワークが要るコマンド（`npm install` など依存の追加・更新）だけは Orchestrator が実行する。その後に続くコードの修正は、通常どおり Codex に委譲する
- Orchestrator が直接変更した場合は、その差分を Codex にレビューさせる（向きを逆にした Review②）。テンプレートAと同じ3項目の形式で返させ、差分を読ませたうえで検証コマンドも実行させる
- Codex のサンドボックスで検証コマンドが失敗したときは、コードの問題か、通信できないことによる失敗か（build でフォントなどを取得する場合がある）を分けて報告させる
- そのうえで Step 4 は省略せず、Orchestrator も自分で行う

## Step 4: Review②

Codexの完了報告を鵜呑みにしない。以下を自分で行う。

1. **diffを全部読む** — 一部ではなく全部。スコープ外のファイルが変更されていないか確認する
2. **検証コマンドを自分で実行する** — Codexが「通した」と言っていても、自分の手で実行する
3. **テストの中身を確認する** — 受け入れ条件を本当に検証しているか。アサーションが骨抜きになっていないか、skipで回避されていないか
4. **修正前のコードでテストが落ちることを確認する** — `git stash push -- <変更したファイル>` で旧コードに戻して実行し、失敗を確認したら `git stash pop` で復元する。落ちないテストは、バグを捕まえていない。新しく追加した関数などで、旧コードに戻すと import エラーで落ちるだけになる場合は、それではバグを捕まえているか分からない。旧コードと同じ振る舞いをする一時モジュールなどで実行して確かめる
5. **受け入れ条件が触れていない変更を、既存コードと見比べる** — 受け入れ条件にもテストにも現れない変更（マークアップの構造、クラス名、配色、余白、命名、ファイル配置、既存ユーティリティを使わず書き起こしていないか）を洗い出し、**同種の既存ファイルを1つ選んで並べて読む**。lintが拾うもの（整形、import順、未使用）はここで見ない。制約に挙げた既存規約に反していれば `required_changes`、好みの差にとどまるなら `notes` とする

問題があれば、テンプレートCに**失敗ログを添えて**、codex-session の手順で同じセッションへ差し戻す。自分の判断は「レビュー出力の形式」で記録する。

**差し戻しは2回まで。** 解決しなければ、前提（Shapeの内容そのもの）を見直すか、人間へ判断を求める。

テスト・build・lint等の失敗を自分の判断で覆さない。失敗している状態でcommitしない。

## Step 5: Ship

以下を報告する。

- 変更概要
- 検証結果（実行したコマンドとその結果）
- 残存リスク — 対応しなかった `notes` や、Review②で見送った指摘もここに含める

commitが許可されていれば、検証コマンドの終了コードを確認し、すべて成功していることを確かめてから、別の手順として commit する。検証と commit を1つのコマンドにまとめない。**今回のタスクに属する変更だけを含める。** Step 1で報告した無関係な差分を含めるかは、人間の判断を仰ぐ。

**pushは指示があったときだけ行う。** 既定ではしない。

commit の後、記録の候補を挙げる。記録の中身のルールは `.claude/skills/record/SKILL.md` に従う。

- record の「記録に値するか」の基準で候補を選び、各候補に記録先と書く内容の要約を添える。候補が無ければ「記録の候補なし」と報告する
- 人が「記録して」と言ったら、record の手順で書く。言わなければ書かない
- マージ後の更新は、人が PR のリンクを添えて頼んだときに record の手順で行う。Ship の時点では、はじめかた・技術構成・運用保守を更新しない（マージ前のため）

codex-session の手順でセッションを畳む（連続するタスクで維持する場合を除く）。

## 委譲プロンプトのテンプレート

委譲プロンプトは都度生成する**自己完結の指示書**である。Codexが他の文脈を参照しなくても実装できる状態にする。

```
## 目的
（1〜2文）

## 受け入れ条件
- （検証可能な形で箇条書き）

## 制約
- 触ってよいファイル範囲：
- 守るべきインターフェース・既存規約：
- 受け入れ条件を検証するテストを追加すること

## 検証コマンド
（Codex自身が実行して通すもの）

## やらないこと
- （スコープ外の明示）

不明点・矛盾・実現不能な点が見つかったら、実装せずに質問を返してください。
```

末尾の一文は必ず入れる。

Review① で出たが採用しなかった notes や、前の版の仕様から外した項目は「やらないこと」に明記する。黙って消すと、同じセッションの Codex が覚えていて実装に入れることがある。

## レビュー出力の形式

Review①でCodexに批評を依頼するとき、およびReview②で自分の判断を記録するとき、出力は次の3項目に固定する。

```
status: pass | revise
required_changes: 先へ進むのを止める指摘（なければ空）
notes: 任意の提案・気づき（非拘束）
```

- `required_changes` のみが先へ進むのを止める。`notes` を過剰実装の理由にしない
- `pass` には根拠を1行添える（根拠のないPASSを許さない）
- 修正→再レビューは2回まで。解決しなければ人間へ

## レビュー依頼のテンプレート

Codexへ送るプロンプトは、下記テンプレートを埋めて使う。送り方は `.claude/skills/codex-session/SKILL.md` に従う。

### A. レビュー依頼（Review①・初回）

```
レビュー依頼です。実装はしないでください。ファイルも変更しないでください。

以下の仕様を読み、曖昧な点・矛盾・実現不能な点を指摘してください。
あわせて、この受け入れ条件をすべて満たしたとして、なお実装者が自由に決められる部分がどこかを挙げ、それが既存コードと食い違いうるなら指摘してください。

## 目的
（Shapeの目的）

## 受け入れ条件
（Shapeの受け入れ条件）

## 制約
（Shapeの制約）

## 検証コマンド
（Shapeの検証コマンド）

## やらないこと
（スコープ外）

出力は次の3項目のみで返してください。

status: pass | revise
required_changes: 先へ進むのを止める指摘（なければ空）
notes: 任意の提案・気づき（非拘束）

pass の場合は、その根拠を1行添えてください。
```

### B. 再レビュー依頼（Review①の差し戻し後）

```
再レビュー依頼です。実装はしないでください。ファイルも変更しないでください。

前回の required_changes に対応し、仕様を修正しました。

## 前回の指摘への対応
- （指摘）→（どう直したか）

## 修正後の仕様
（差分ではなく全文を載せる）

同じ3項目の形式で返してください。
```

**修正後の仕様は全文を載せる。** 差分だけ送ると、Codexが古い前提と混ぜて読む。同一セッションを使い続ける以上、古い前提は会話に残り続けるため、上書きする形で送る。

### C. 差し戻し（Review②）

```
差し戻しです。以下の問題があります。修正してください。

## 問題
（何が起きているか）

## 失敗ログ
（コマンドと出力をそのまま貼る。コマンドの失敗がないレビューでの指摘なら、その根拠を書く）

## 期待する状態
（受け入れ条件のどれを満たせていないか）

制約は委譲時から変わりません。スコープ外のファイルには触らないでください。
指示した箇所以外のアサーションを削除・緩和したり、skipでテストを通したりしないでください。
修正後、指定の検証コマンドを通してから報告してください。

原因が分からない、または指示に矛盾がある場合は、実装せずに質問を返してください。
```

AとBは**実装させない**依頼、Cは**実装させる**依頼である。取り違えないこと。
