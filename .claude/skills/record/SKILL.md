# record

学び・決定を Notion に記録する手順。役割は2つある。

- **記録する** — ナレッジDB にページを作るか、案件ページの決定ログの先頭に追記する
- **マージ後の更新** — 決定ログの反映欄を「未マージ」から PR のリンクに書き換え、影響欄に挙げた場所を main の状態に上書きする

**記録するかどうかは必ず人が決める。** このSkillが自分の判断で記録を始めることはない。人の確認は1回にする。

- **develop の Ship から** — 候補を挙げるとき、各候補に記録先（3）と書く内容の要約を添える。人が「記録して」と言ったら、そのまま書く
- **人が一言で頼んだとき** — 記録先と書く内容の要約を1回だけ示し、了承を得たら書く

## 1. 設定を読む

プロジェクトの `.claude/notion-record.json` を読む。

```json
{
  "project_page_id": "（この案件の案件ページのID）",
  "knowledge_data_source_id": "f4a40798-b0e6-421a-91e9-7d69745b5ad9"
}
```

ファイルが無い、または使う値が空なら、**記録せずに人に知らせる。** ID をこのSkillや会話から推測して補わない。

## 2. 記録に値するか

記録するのは次のものだけ。

- 次に同じ問題を踏んだ人の時間を節約できる学び
- 設計・インターフェース・運用のやり方を変えた決定

書かないもの：一度きりの操作ミス、公式ドキュメントを読めば分かること（リンクで足りる）、感想・反省。

Ship で候補を挙げるときはこの基準で絞る。人が基準に当たらないものを頼んだときは、その旨を伝えたうえで人の判断に従う。

## 3. 記録先を決める

**「別の案件でも同じ問題を踏みうるか」** だけで判断する。

| 判定 | 記録先 |
| --- | --- |
| 踏みうる（技術・ツール・ライブラリに起因） | ナレッジDB |
| 踏まない（この案件の事情・仕様・経緯に起因） | 決定ログ |
| 基準を当てても決まらない | 決定ログ（後でナレッジへ昇格できるが、逆は分かりにくい） |

両方に関わるときは、ナレッジに書き、決定ログからそのページをメンションする。**本文を両方に書かない。** 重複した内容は片方が必ず古くなる。

## 4. 書き方

ページの見出し構造は Notion のテンプレート（案件ページ・ナレッジともデフォルトに設定済み）に従う。テンプレートの見出しをそのまま使い、自分で見出しを書き足して二重にしない。

### ナレッジ

- **タイトル** — 現象を1行で書き、関わる技術名を含める。対処や分類をタイトルにしない
  - 良い：`（Next.js）npm run dev を動かしたまま npm run build すると .next が壊れて build が失敗する`
  - 悪い：`rechartsのバグ対応`
- **タグ** — 1〜2個。既存の選択肢から選ぶ（`API-retrieve-a-data-source` で読める）。どれでも表せないときだけ、人に確認して新しく足す
- **関連案件** — 設定の `project_page_id`。案件に紐づかない学びなら空でよい
- **本文** — 現象・原因・対処・参考
  - エラーメッセージやコマンドはコードブロックにして、そのまま貼る
  - 原因が分からなければ「未特定」と書く。分からないから書かない、にしない
  - 対処のうち、試していない代替案は「未検証」と明記する
  - 参考が無ければ省略する

### 決定ログ

見出しは `YYYY-MM-DD 決定の見出し`。その下に4項目を置く。

- **決定** — 何を決めたか
- **理由** — なぜそうしたか。ナレッジに関わるならそのページをメンションする
- **影響** — マージ後に、はじめかた・技術構成・運用保守のどこを更新するか。無ければ省略
- **反映** — Ship の時点では `未マージ（ブランチ名）`。コード変更を伴わない決定なら `なし`

**影響欄は、マージ後の更新で使うチェックリストになる。** 決定がはじめかた・技術構成・運用保守に関わるなら必ず書く。漏れやすいので、案件ページの該当セクションを読み、小見出し（デプロイ手順・定期作業・障害時の初動・シークレットの在り処など）を1つずつ当てて確かめる。影響欄には次の2つを挙げる。

- **変更によって古くなる記述** — 同じ事柄が書かれている場所すべて（はじめかたと障害時の初動の両方、など）
- **マージ後の main で新しく見えるようになるもの** — 直した結果として見える既知の不具合など

決定ログは追記のみ。過去の項目を書き換えてよいのは反映欄と、5の手順で影響欄に漏れを足すときだけ。

### 書かないもの

**シークレットの値（トークン、APIキー、パスワードなど）は絶対に書かない。** 在り処だけ書く（例：`OPENAI_API_KEY` → Vercel の Environment Variables）。エラーログやコマンドを貼るときも、値が混ざっていないか確かめる。

## 5. マージ後の更新

人から PR のリンクを受け取って行う。

1. `gh pr view <PRのURL> --json state,number,url` で、マージ済み（`MERGED`）であることを確かめる。未マージなら更新しない
2. main のリポジトリ（6の定義）と、ブランチを push したリポジトリ（フォーク運用なら別）を `git fetch` する
3. 案件ページを読み、反映欄が `未マージ（<ブランチ名>）` の項目を**すべて**拾う。PR のブランチ名だけで探さない。ブランチを積み上げていると、最後のブランチの PR をマージした時点で前のブランチも main に入っている
4. 拾った項目それぞれについて、そのブランチが main に含まれているかを確かめる

   ```bash
   git merge-base --is-ancestor <ブランチ> <mainのremote>/main; echo $?
   ```

   `<ブランチ>` は、リモートにあれば `<ブランチのremote>/<ブランチ名>`、無ければローカルの `<ブランチ名>` を使う。ブランチを積み上げたときは、最後の1本だけを push し、前のブランチはローカルにしか無いことが多い

   - `0` → 含まれている。対象にする
   - `1` → 含まれていない。「未マージ」のまま残す
   - それ以外（リモートにもローカルにもブランチが無いなど）→ 人に確認する
   - squash・rebase でマージした場合、コミットが変わるため含まれていても `1` になる。PR がそのマージ方式なら、判定を人に確認する
5. 対象の項目の反映欄を `[#<番号>](<PRのURL>)` に書き換える
6. 上書きする前に、本番のデプロイが成功したかを GitHub に残った結果で確かめる

   ```bash
   gh pr view <PR> --json mergeCommit
   gh api repos/<owner>/<repo>/commits/<マージコミット>/status
   ```

   デプロイのサービス（例：`context` が `"Vercel"`）の `state` で判定する。人が「本番は確認済み」と言っていても、結果が残っていればそちらで判定する

   - `success` → 上書きしてよい
   - `failure` → 上書きしない。main と本番がずれているので、人に報告する
   - `pending` → 待ってから読み直す
   - デプロイの結果が残っていない → 人に確かめる（GitHub と連携していないデプロイ先、デプロイしていない案件など）
7. 対象の項目の影響欄に挙げた場所を、**main の状態に上書きする**
   - main は、本番のデプロイ元（デプロイしていなければ、正とするリポジトリ）の main。どのリポジトリかは、はじめかたの冒頭に書いてある
   - fetch したそのリポジトリの main を読んで書く。作業ブランチや手元の未コミットの状態を書かない
   - 上書き型なので履歴は残さない。経緯は決定ログが持つ
8. 上書きしていて、影響欄に無い場所も直す必要があると分かったら、それも直し、影響欄に書き足す（上書きと影響欄の対の更新）
9. 更新した場所を人に報告する

## 6. Notion の操作

Notion MCP（`mcp__notion__*`）を使う。画面に手で貼らない（見出しの二重化、コードブロックの崩れ、タイトルの初期値の残り、メンションの入れ方で詰まる）。

| やること | 手順 |
| --- | --- |
| ナレッジのページを作る | `API-list-data-source-templates` でデフォルトのテンプレートがあることを確かめ、`API-post-page` に下の形で渡す。**データベースIDではなくデータソースIDを使う。** タイトル・タグ・関連案件は `properties` で作成時に入れる（入れないとタイトルがテンプレート名のまま残る） |
| 本文を埋める | 作ったページを `API-retrieve-page-markdown` で読み、テンプレートの見出しの下を `API-update-page-markdown` の `update_content` で置き換える |
| 決定ログの先頭に追記する | `API-get-block-children` で案件ページのブロックを読み、「決定ログ」見出しのIDを取る。`API-patch-block-children` の `after` にそのIDを渡して、見出し＋4項目のブロックを入れる |
| ページをメンションする | rich text の `{"type": "mention", "mention": {"page": {"id": "<ページID>"}}}` で入れる |
| 1行の書き換え・見出しの下の置き換え | `API-update-page-markdown` の `update_content`（検索・置換） |

`API-post-page` の引数（2026-10-10 にナレッジDBで通ることを確かめた形）。

```json
{
  "parent": {"type": "data_source_id", "data_source_id": "<knowledge_data_source_id>"},
  "template": {"type": "default"},
  "properties": {"タイトル": {"title": [{"text": {"content": "<タイトル>"}}]}}
}
```

注意。

- **置換の前に `API-retrieve-page-markdown` でページを読み、返ってきた文字列のまま `old_str` に使う。** 見た目と違う（改行は `<br>`、メンションは `<mention-page url="…"/>` になる）。画面の見た目から検索文字列を組み立てない
- **リンクは必ず `[表示名](URL)` の形で書く。** URL をそのまま書くと、後ろの文字までリンクになる
- `API-update-page-markdown` の `insert_content`・`replace_content_range` は非推奨なので使わない。`replace_content` はページ全体を置き換えるので使わない
- `API-update-a-block` は基本使わない。使うなら、ブロックの種類（`paragraph` など）をトップレベルの引数として渡す必要がある。また `archived` の既定値が `true` と定義されているため、省略せず `false` を明示する
- テンプレートから作ったページの中身（見出し）がすぐ読めない場合は、少し待って読み直す。テンプレートの適用が作成より遅れることがある
- 404 が返ったら、ページがインテグレーションに共有されていない可能性が高い。人に共有設定を頼む
- 書き終えたら `API-retrieve-page-markdown` で読み直し、見出しの二重化・リンク切れ・崩れが無いことを確かめてから、ページのリンクを人に報告する
